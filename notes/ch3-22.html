ch3_22 event_1（事件使用方式）

前兩堂的 Message 很適合在父子階層裡喊話；但如果要通知 UI、音效、GameManager 這些彼此沒有父子關係的物件，就會開始卡住。這堂先介紹 Event 為什麼會出場。

EVENT · MESSAGE · DECOUPLING

不是跑去叫每個人，而是宣布：「某件事發生了」

課程用「玩家 HP 歸零」當例子。死亡時可能要同時播放音效、更新 UI、觸發其他遊戲效果，但這些物件不一定和 Player 有任何父子階層關係。

01Message 的限制很在意父子階層 02Event 的直覺像警報鈴 03Message vs Event叫人做事 vs 宣布事情 04整堂模型HP 歸零 → 多系統反應
01

Message 的限制：大家如果不住在同一棵 hierarchy，就很難喊到

課程先假設玩家 HP 歸零。這時可能要同時做很多事情：

Player HP = 0
      ↓
播放死亡音效
顯示死亡 UI
觸發其他遊戲效果
...

問題是，負責這些工作的物件不一定是 Player 的父物件或子物件，甚至可能全部都和 Player 平行：

Player
UIManager
AudioManager
GameManager

這種結構下，前面的 BroadcastMessage 往下傳、SendMessageUpwards 往上傳，都不適合拿來通知這些平行物件。

問題核心Message 很依賴 Transform 階層；沒有父子關係時，它的用途就會受限。
02

Event：像按下一顆警報鈴

這堂先把 Event 想成「某件事情發生了，我公開宣布一次」。有需要對這件事反應的系統，再各自處理自己的工作。

          「Player 死亡了！」
                  ↓
               🔔 Event
            ↙      ↓      ↘
      Audio      UI      其他系統
        ↓         ↓          ↓
      播音效    顯示畫面    做自己的事

五歲版：Player 不需要一個一個跑去敲門叫大家。它只要按下警報鈴，平常有在聽這顆鈴的人，就知道「現在輪到我做事了」。

Event我不指定你一定要做什麼，我只宣布：「這件事發生了。」
03

Message vs Event：一個像叫人，一個像公告

Message
→ 「我要叫這個階層範圍裡的人做事」
→ 很在意自己 / 父物件 / 子物件

Event
→ 「某件事情發生了」
→ 需要反應的人自己處理
→ 不需要靠父子階層才能通知

課程這堂的重點不是說 Message 完全沒用，而是當接收者彼此沒有合適的階層關係時，Event 會更適合。

一句話分辨Message 比較像「我叫你做事」；Event 比較像「我宣布事情發生了」。
04

把整堂壓成這個模型

玩家 HP 歸零
      ↓
需要很多系統一起反應
      ↓
但這些物件沒有父子階層關係
      ↓
Message 不方便
      ↓
改用 Event
      ↓
「PlayerDead 發生了」
      ↓
有需要的系統各自處理
